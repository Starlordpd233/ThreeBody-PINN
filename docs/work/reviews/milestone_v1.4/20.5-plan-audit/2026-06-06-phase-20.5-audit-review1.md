The expected values (# expect 1) are correct, so the assertions will pass/fail properly. But the comments tell the executor that a bare count "would be 2" — which is wrong. Why it matters: An autonomous agent reading the comment might think 1 is a failure mode (since the comment says "bare-phrase count would be 2") and STOP unnecessarily.

Finding 4 — LOW · Operational Resilience

Probe assertion for velocity scaling encodes an implicit code-behavior assumption

The probe's Test 2 computes:

expected_v2 = norm.ppf(synthetic[:, 4:7], loc=0, scale=0.1) * expected_scale[:, None]

This encodes the assumption that ic_generation_utils.py multiplies velocity by the scale factor after the inverse-CDF transform (lines 165→176 in the code):

v2_batch = self._map_sobol_to_velocity(u_vel)   # inverse CDF
# ... later:
v2_batch = v2_batch * scale[:, np.newaxis]        # multiply by s

The plan's spec edits describe the Sobol coordinate allocation but do not explicitly state this "velocity scaled by s" behavior. If the code's velocity-scaling order changes (e.g., scaling applied before inverse CDF), the probe would correctly fail — but the failure message ("velocity not from columns 4-6") would misdiagnose the root cause as a column-allocation error rather than a scaling-order difference.

Fix: Add a comment in the probe clarifying the scaling-order assumption, or add a separate assertion for the scaling behavior. Low urgency — the probe is disposable.
