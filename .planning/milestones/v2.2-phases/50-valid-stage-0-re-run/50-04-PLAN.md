<objective>
Repair the one implementation divergence that made the Phase-50 band impossible,
then re-pin the recipe so a fresh generation can open.

`RunController._run_validation` builds its batch with the DATA-05 **training**
batch constructor, which draws `replay_count` identities without replacement. At
Stage 0 the held-out validation pool is smaller than that draw, so DATA-06
`StageZeroUnderpopulated` is raised at the first validation event and no band can
exist. `ctl_instruction.md:1815-1817` scopes `B_replay = 240` to "a 256-trajectory
**training** batch"; `ctl_instruction.md:1938-1940` puts the ADVANCE success gate
on "the **held-out validation set**"; and `compute_validation_gate` — firing on the
same `validation_every` branch — already reads `sorted(records_at_or_below(stage))`.
The two consumers of "the validation set" at one event disagree. This plan makes
them agree.

This is a conformance repair of an implementation divergence against the spec, on
the CONF-08/CONF-09 precedent — not recipe tuning. No constant is set from the
observed pool size, and `replay_count` stays 240 as the training contract. See
GAP-50-02 in `50-GAPS.md` for the owner ruling and the rejected alternatives.
</objective>
