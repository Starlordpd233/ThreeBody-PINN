## Scope Note

Plan 33-01 intentionally groups the packet-first artifacts despite touching ten listed files because they are one tightly coupled process unit: the baseline sentinel, Phase 33 packet schema, five Phase 33-owned packets, one ledger synchronization, and the plan summary. Splitting this bundle would create a higher-risk partial state where some Phase 33-owned rows have packets but the shared ledger does not yet link them, or where spec-edit plans could start before the packet-before-edit prerequisite is complete. The plan makes no framework-spec edit, no runtime-code edit, no generated-data edit, no package/schema change, and no UI artifact; all writes are Phase 33 planning/evidence files plus the single Phase 32 ledger link required by the existing packet-before-edit mandate.

## Acceptance-Check ID Convention (surfaced per AGENTS.md process-artifact rule)

Phase 33 standardizes one acceptance-check-ID convention across the evidence packets, the Phase 32 ledger Acceptance Check IDs, and the Plan 04 verification checks. The five Phase 33-owned findings map to exactly these AC IDs:

| Finding row (Phase 32 ledger) | Acceptance Check ID | Packet |
|---|---|---|
| `adaptive stage assignment` | `AC-CURR-01` | `adaptive-stage-assignment.md` |
| `L_max / tau_L` | `AC-CURR-02-LMAX` | `l-max-tau-l.md` |
| `M7` | `AC-CURR-02-M7` | `m7-tau-l-ic13-exclusion.md` |
| `D5` | `AC-CURR-03` | `d5-stage-transitions.md` |
| `M6` | `AC-CURR-04` | `m6-l-norm-metadata.md` |

The Phase 32 ledger previously seeded the `L_max / tau_L` row as `AC-CURR-02` and the `M6` row as `AC-CURR-04-M6`. Phase 33 renames those two to `AC-CURR-02-LMAX` and `AC-CURR-04` respectively, because (a) `CURR-02` covers both the `L_max` row and the separate M7 `tau_L`-exclusion row, so the `L_max` row needs the disambiguating `-LMAX` suffix to coexist with `AC-CURR-02-M7`; and (b) the `-M6` suffix on `AC-CURR-04` was redundant — `M6` is the only `CURR-04` ledger row. This rename is a process-artifact-schema change; it is recorded here (rather than applied silently) so the executor and any reviewer see one stable convention. Plan 04 Task 2 applies these IDs to the ledger as the final transition; Plan 01 Task 3 only links the packet paths and seeds the same IDs so the convention is consistent before any spec edit.
