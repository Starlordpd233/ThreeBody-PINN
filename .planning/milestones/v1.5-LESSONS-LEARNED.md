# v1.5 Issue-02 — Lessons-Learned Retrospective (Meta-Workflow)

> **What this is.** High-level retrospective on *how* we worked Phases 23–24 of milestone v1.5 (the research-context-bundle → individual-external-research → consolidation → final-resolution-doc pipeline), not *what* we found about the data pipeline itself. The technical findings live in the resolution doc and DATA-07 addendum; this document is about the workflow that produced them.
>
> **Who should read it.** The next milestone's agents (Issue-03 prep) and the next meta-milestone's retrospectives (e.g., v1.6). Anyone choosing between "do this manually" and "re-run the external-research pipeline" should read Theme 1 + Theme 2.
>
> **Evidence trail.** Every claim is cited to a file path, commit hash, or claude-mem observation ID. Raw extraction is in `.planning/milestones/v1.5-LESSONS-LEARNED-raw-timeline.md` (consumed after the deliverable is committed).

## Executive Summary

1. **The two-stage external-research pipeline is reproducible.** Stage 1 sends a generic prompt + self-contained research package to 8 independent research agents; Stage 2 sends all 8 reports (anonymized R1–R8, bundled into one file) plus the package to one consolidation agent. The 4-file upload set (master, specs bundle, research bundle, DATA-07 addendum), R1–R8 anonymization, in-prompt crosswalk, and 3-pass Method (consistency / completeness / output-contract conformance) all worked. The main surprise was that the crosswalk vocabulary should have been locked at plan-authoring time, not execution time (GAP-23-01).

2. **Mechanical work is a first-class deliverable, not a side effect.** The `make_bundles.py` builder with SHA-256 self-verification, the BUNDLE-MANIFEST with self-ID scan, and the forensic quarantine pattern (`simulation_data/Data/forensic/`) each required design attention and atomic commits. The bundle's byte-verbatim guarantee meant a single collision would abort — the collision check caught zero real collisions but its presence eliminated an entire class of "did the upload corrupt?" questions.

3. **The STOP protocol + gap registers worked as designed, but both gaps that fired were planning-time gaps caught at execution time.** GAP-23-01 (R6 crosswalk non-mechanical mappings) and GAP-24-01 (DATA-05 mass-drift baseline) both surfaced during the consolidation/packaging phase, not during planning. Pre-emptive scans during the discuss phase would have caught them earlier. The 11-field gap register schema (including the math/engineering grounding requirement) forced the agent to demonstrate *why* each gap was consequential before recording it.

4. **Commit hygiene and concurrent-sessions awareness are mandatory infrastructure, not nice-to-haves.** The `scripts/agent-commit` wrapper, `Agent-Assisted-By` trailer, and atomic-commit discipline kept a 24-commit Phase 23–24 trace re-derivable. The concurrent-sessions commit race (discovered when two Claude sessions on `milestone/v1.5` produced divergent commits) is now memorialized in MEMORY.md and the mitigation (`git status --short --branch` + `git log --oneline -5` at session start) is cheap enough to run every time.

5. **Tooling decisions compound across phases.** `ctx_batch_execute` with `concurrency: 4` for parallel I/O, claude-mem's 3-layer workflow (search → timeline → get_observations) for session memory, and parallel `Explore` subagents for read-only crosswalk verification (8 columns verified in ~5 min instead of ~30 min sequential) are the right patterns for any new milestone.

6. **Forward-looking: insert a resolution-doc readiness-verification phase before adjudication.** The Stage-2 consolidation agent produces the candidate verdict source, but nothing in the Phase 23–24 workflow verifies that output is *fit for adjudication* before Phases 25–29 commit to it. A lightweight "Phase 24.5" — a checklist-driven readiness gate that verifies section completeness, output-contract conformance, and cross-reference integrity — would catch consolidation defects before they propagate into five phases of adjudication work. If the doc fails the gate, the consolidation agent fixes it before adjudication starts. This phase also serves as a preview/mapping resource: later phases know exactly where the resolution doc lives, what it provides, and how to navigate it.

## Theme 1 — Prompt design for the external research pipeline

**Context.** v1.5's external-research pipeline (same two-stage shape as v1.4's) works as follows: Stage 1 sends the external-research-agent prompt verbatim to multiple independent research agents (we used 8); each produces an individual research report. Stage 2 sends the consolidation-agent prompt plus the four attached files to one final consolidation agent. The Stage-2 output is the *candidate verdict source* for adjudication Phases 25–29. Both prompts are committed under `docs/work/plans/milestone_v1.5/23-research-package-assembly/`.

### What we did

- **Stage-1 prompt** (`2026-06-10-phase-23-issue-02-external-research-agent-prompt.md`): a generic wrapper that contains no research direction — all questions, constraints, claims, and context live in the research package files. The prompt defines the agent's role, the task (read the master → answer every framed question → produce a resolution doc), and ground rules (the package is the complete input; respect authority levels; the issue doc is non-authoritative reference).
- **Stage-2 prompt** (`2026-06-10-phase-23-issue-02-consolidation-agent-prompt.md`): revised three times in one day. The final version names exactly 4 attached files (master, specs bundle, anonymized R1–R8 research bundle, DATA-07 addendum), embeds a 14-question × 8-report verdict crosswalk (navigation aid, non-authoritative), and defines a 3-pass Method: consistency (do reports agree?), completeness (any question unaddressed?), and output-contract conformance (does the output match the required section structure?).
- **The 4-file upload set** fits in a single bundle message; it's deterministic and self-verifying via delimiter + SHA-256. Reports are anonymized as R1–R8 with the tag→file mapping recorded only in the in-repo BUNDLE-MANIFEST (never uploaded).
- **The crosswalk matrix** (14 rows × 8 columns, embedded directly in the prompt) lets the consolidation agent navigate reports without loading full bodies into context. Each cell uses exactly four forms: `<verdict gist> (<section>)`, `matrix-only (<section>)`, `—`, or `see <section>`.
- **The 3-pass Method** was strengthened late: the output-contract conformance pass (commit `5c60f014`) was added after a 14-cell R6 crosswalk gap was caught (GAP-23-01). It verifies the output document has every required section before the agent signs off.

### What worked

- The 4-file upload set is the right abstraction. It fits in one message, is deterministic, and the SHA-256 evidence trail makes byte-preservation re-derivable.
- Anonymizing reports as R1–R8 with a non-uploaded BUNDLE-MANIFEST eliminates model-name anchoring while keeping provenance traceable repo-side.
- The crosswalk matrix embedded in the prompt (never load full report bodies into context — the 8 reports total ~491 KB) is both a navigation aid for the consolidation agent and a verification artifact for the project.
- The Independence ground rule (reports are "argued candidate positions, nothing more") mitigates the byte-size self-ID concern (R4 notably so at 126 KB).

### What to repeat

- The 4-file bundle format, R-anonymization pattern, and 3-pass Method transfer as-is to Issue-03.
- The crosswalk should be drafted at plan-authoring time with the four cell forms defined up front — the GAP-23-01 detour cost ~30 min of agent + user time that could have been avoided.
- The output-contract conformance pass should be in the prompt from the start, not added by a follow-up commit.

### What to avoid / adapt

- The R6 crosswalk column had non-mechanical mappings (Q-A6..Q-C4 rows plus "Seed Conflict" → Q-C1 alias) that should have been surfaced during prompt authoring, not execution. Define the full cell vocabulary and alias mapping at plan time.
- The prompt was revised three times in one day (commits `63c4bf1a`, plus the crosswalk addition, plus the output-contract pass `5c60f014`). This is acceptable iteration but signals the upstream design could be tighter.
- **Emerging gap (2026-06-11):** the pipeline has no verification step between "consolidation agent delivers the resolution doc" and "adjudication phases begin." The user plans to insert a lightweight readiness-verification phase (see §"Forward-looking: resolution-doc readiness gate" below) before Phase 25. Issue-03 should bake this gate into its workflow from the start.

## Theme 2 — Mechanical work as a first-class deliverable

**Context.** The consolidation packaging task was not "gather some files." It was a small software engineering project: a deterministic Python builder with collision detection and SHA-256 self-verification, a manifest with self-ID scan, a forensic quarantine for stale artifacts, and a 3-step .gitignore reconciliation. Each of these required design attention, atomic commits, and verification.

### What we did

- **Bundle builder** (`make_bundles.py`, commit `dedae1c3`): reads 8 report files + 5 spec files, checks every source for delimiter collisions, emits two bundles with `===== BEGIN/END` delimiters, re-reads and SHA-256-compares every extracted section against its original, and writes BUNDLE-MANIFEST.md with hashes, byte counts, R-tag mapping, and self-ID token hit counts. The self-test exercises round-trip byte-exactness including files without trailing newlines and multi-byte UTF-8, plus the negative collision-detection path.
- **BUNDLE-MANIFEST** (commit `8fa52179`): the committed evidence that byte-preservation is re-derivable. Contains per-section SHA-256 hashes, the R-tag→filename mapping (deliberately NOT uploaded), and a self-ID scan showing which reports mention model/vendor names. Anonymization is best-effort at the packaging layer; the manifest records honestly.
- **Forensic quarantine** (commit `8b52f6c0`): 70 invalid base-hierarchical Brutus outputs (IDs `0005`–`0059`, `0061`–`0075`) were archived to `simulation_data/Data/forensic/data05_gap24-01_old_outputs/` with a committed SHA-256 manifest. The quarantine is permanent — old artifacts stay out of training and metrics.
- **.gitignore reconciliation** (commits `338baa8d`, `2dfa3211`): three rounds of .gitignore additions for forensic outputs, scratch outputs, and understand-anything intermediates. The forensic directory was initially added, then reverted (metrics were already committed), then re-added with a narrower pattern targeting only the untracked old outputs.

### What worked

- Deterministic, byte-verbatim bundling with collision-checked delimiters. The `make_bundles.py` self-test caught zero real collisions, but its presence eliminated an entire class of "did the upload corrupt?" questions.
- SHA-256 evidence trail: every section's hash is recorded in the manifest, and the manifest is committed. The claim "bundles are byte-identical to originals" is re-derivable by anyone with the repo.
- Staged remediation for DATA-05: re-stage 70 of 70 → validate → re-run probe → 0/4857 mismatches → user approval → swap → re-generate metrics. Each step was its own atomic commit, making the remediation trace auditable.
- The forensic quarantine pattern (archive stale artifacts with a committed hash manifest, never delete) is the right default for any data-integrity anomaly.

### What to repeat

- The bundle builder + manifest + SHA-256 evidence pattern transfers as-is to Issue-03.
- The forensic quarantine pattern (archive with hash manifest, never delete) should be the default response to any data-integrity anomaly.

### What to avoid / adapt

- The .gitignore dance (add forensic dir → revert because metrics were already committed → re-add with narrower pattern) was a 3-step iteration. Next time: check `git ls-files` for tracked-vs-untracked before writing the .gitignore pattern.
- The forensic, scratch, and understand-anything exclusions were all added late in the milestone. Consider a `.gitignore` template that new milestones copy forward on day one.
- The bundle builder's self-ID scan is informative but not actionable — it tells you which reports self-identify but doesn't scrub them. If model-name anchoring becomes a concern for Issue-03, decide up front whether to scrub report bodies or accept the risk.

## Theme 3 — STOP protocol + gap registers as the system-of-record

**Context.** The STOP protocol (CLAUDE.md §"v1.5 applicability") is the project-wide governance rule: when source materials are silent or ambiguous on a semantic decision, stop work, record a gap in the phase-local register, update the milestone-wide index, and surface to the user. The gap register has 11 required fields including the math/engineering grounding requirement (added 2026-05-19). Two STOP-protocol gaps fired during Phases 23–24.

### What we did

- **GAP-23-01** (R6 crosswalk non-mechanical mappings): the R6 report's decision matrix is keyed by issue IDs (B-06, B-11, M11, M12, M13, D7, M16, "Seed Conflict"), not Q-IDs. Six rows map mechanically via the crosswalk's own parentheticals; the remaining mappings (Q-A6..Q-C4, whether M16 §3.7 maps to any crosswalk row) required user instruction. The gap entry records: the decision point, where it surfaced (the crosswalk R6 column), the task context, the classification (semantic), the source silence, the math/engineering grounding (why this is consequential), what the agent was tempted to decide, and the user's A/B/C options. Resolution: all 14 R6 cells filled per user instruction; shape-check passed.
- **GAP-24-01** (DATA-05 hierarchical mass-drift baseline): the mass-drift probe found 70 base-hierarchical outputs (IDs `0005`–`0059`, `0061`–`0075`) where `m_IC` from `simulation_data/Data/ic_final/ic_hierarchical/` files did not match the t=0 mass column in the corresponding Brutus output. The gap entry's math/engineering grounding demonstrates *why* this is consequential: the hierarchical IC perturbation pipeline may have altered masses between IC generation and Brutus input, and if so, every downstream metric and training datum for those 70 IDs is invalid. Resolution: current ICs are canonical; the 70 outputs are stale artifacts; rerun from current ICs (executed and validated same day: 70/70 passed, post-swap probe 0/4857).

### What worked

- The 11-field gap register schema forces the agent to demonstrate understanding before recording. The math/engineering grounding field is the key innovation: it prevents "I don't know why this matters but the source is silent" gaps from cluttering the register.
- The `RESOLVED-WITH-INSTRUCTION` status string is grep-able proof that the gap was closed by user instruction, not by the agent inventing.
- The milestone-wide index (`.planning/milestones/v1.5-GAPS.md`) gives a one-glance view of all open/resolved gaps across phases.
- The gap register doubles as an audit trail: GAP-24-01's entry records not just the decision but the full remediation scope (affected IDs, canonical source, invalid artifacts, decision boundary).

### What to avoid / adapt

- Both gaps fired *during* the consolidation/packaging phase, not during the planning phase. The plan author should pre-emptively scan prompt files for the 4-cell crosswalk vocabulary and pre-emptively run a `np.allclose` baseline check during discussion. The cost of a pre-emptive scan is ~5 min; the cost of a mid-execution STOP gap is ~30 min + context switch.
- The gap index had to be restored after a prior session dropped GAP-24-01 (commit `0df9f15b` — `docs(planning): restore gap-24-01 and add gap-23-01 to v1.5 gap index`). This is the concurrent-sessions race manifesting in the gap register. The mitigation: treat the gap index as a shared resource and verify it at session start.
- For Issue-03, add a pre-emptive gap scan to the discuss-phase checklist: (1) audit the prompt's crosswalk vocabulary, (2) run a `np.allclose` baseline on any data the prompt references, (3) verify every alias mapping is mechanical.

## Theme 4 — Commit hygiene + concurrent-sessions race

**Context.** The repo uses `scripts/agent-commit` (a wrapper) for every agent commit; raw `git commit` is blocked by lifecycle hooks. Every agent-assisted commit must include `Agent-Assisted-By: <agent/tool/model>`. Tags `v1.5-pre-phase-NN` are cut from `milestone/v1.5` HEAD at the start of each phase. A concurrent-sessions commit race was discovered during Phase 24 when two Claude sessions on the same branch produced divergent commits.

### What we did

- **Agent-commit wrapper**: every commit in Phases 23–24 used `GIT_AGENT_ID="Claude Code (claude-fable-5)" scripts/agent-commit -m "..."` with a typed commit message (`feat(23)`, `docs(23)`, `evidence(24)`, `verify(24)`, `chore(governance)`) and an `Agent-Assisted-By: Claude Code (claude-fable-5)` trailer.
- **Atomic commit discipline**: the consolidation packaging work was decomposed into a 6-part atomic commit plan (claude-mem obs 857), executed as 8 atomic commits: resolution docs, forensic metrics, .gitignore, STATE.md, v1.5-GAPS.md, understand-anything refresh, and two governance commits. Each commit is one logical unit.
- **Concurrent-sessions race**: discovered when two Claude sessions on `milestone/v1.5` produced divergent commits (claude-mem obs 876). The root cause: neither session re-verified `git log` freshness before committing. The race is now memorialized in MEMORY.md as `project-concurrent-sessions-commit-race.md` (claude-mem obs 878).
- **Plan-execution provenance**: the consolidation packaging plan (`docs/superpowers/plans/2026-06-11-issue02-consolidation-packaging.md`) was marked `execution_status: executed` with `Plan-Execution: first-pass` and `Plan-Source:` trailers.

### What worked

- The `scripts/agent-commit` wrapper enforces the typed-message convention and `Agent-Assisted-By` trailer. It's impossible to accidentally commit without provenance.
- Atomic commits per logical unit make the commit trace re-derivable: each commit's `--stat` tells you exactly what changed and why.
- The `v1.5-pre-phase-NN` tags are cheap recovery points. If a phase goes sideways, you can reset to the pre-phase tag without losing earlier work.

### What to avoid / adapt

- The concurrent-sessions race is a recurring tax on parallel sessions. The mitigation (`git status --short --branch` + `git log --oneline -5` at session start AND before each commit) is already mandated by CLAUDE.md but wasn't always followed. For Issue-03, add a pre-commit hook reminder.
- The `Agent-Assisted-By` trailer is easy to omit when copying a commit message from a script. The consolidation prompt commit (`63c4bf1a`) was initially committed with a raw message; it was later amended.
- The 70-forensic-metric commit (`8b52f6c0`) was large but atomic; the consolidation prompt commit (`63c4bf1a`) is mid-sized. Both fit the "one logical unit per commit" rule. The .gitignore commits (`338baa8d`, `2dfa3211`) are small and focused.

## Theme 5 — Tooling + subagent patterns

**Context.** The repo has three agent-tooling pillars: context-mode (raw bytes stay out of context), claude-mem (auto-captured session memory), and the Sequentialthinking MCP. Subagents are used for parallel read-only verification. The consolidation packaging work used all three plus a new pattern: 8 parallel `Explore` subagents for crosswalk column verification.

### What we did

- **`ctx_batch_execute` for parallel I/O**: the consolidation packaging plan's reconnaissance phase used `ctx_batch_execute` with `concurrency: 4` to read 8 files in parallel, with auto-indexed output and inline queries. This kept raw file bytes out of context while still making content searchable.
- **`ctx_execute_file` for in-sandbox file analysis**: the "never load a 491 KB report body into context" rule (from the consolidation packaging plan's `Execution context`) was enforced by using targeted extraction commands (`python3 -c "..."` to extract decision matrices, `grep -nE "^#"` for heading maps) instead of reading full report files.
- **claude-mem 3-layer workflow**: search (get index with IDs) → timeline (get context around interesting results) → get_observations (fetch full details only for filtered IDs). This kept session-history extraction at ~50 observations instead of ~500.
- **Parallel `Explore` subagents for read-only verification**: the crosswalk's 8 columns were verified by 8 independent subagents, each checking one report's column against its source. Sequential verification would take ~30 min; parallel took ~5 min. The pattern: each subagent gets the same prompt template with the column and report path substituted.
- **Sequentialthinking MCP**: used for theme clustering during this retrospective's synthesis phase (per project CLAUDE.md mandate).

### What worked

- `ctx_batch_execute` with `concurrency: 4` is a good default for I/O-bound reconnaissance. The tool's own concurrency ceiling (`min(16, cpu cores - 2)`) was never approached.
- Parallel `Explore` subagents for read-only verification (one per source file, independent checks, merge results) is the right pattern for any task where N sources need the same verification applied.
- claude-mem's session-level memory captures *why* a decision was made; git log captures *what* was done. Both are needed for a complete retrospective.
- The "never load large files into context" rule (enforced by using targeted extraction + `ctx_execute_file`) kept the agent's context budget available for actual analysis.

### What to avoid / adapt

- `ctx_batch_execute` output is auto-indexed, not echoed in full. This is the right behavior, but you must pass `queries` in the same call to get the matching sections — a follow-up `ctx_search` is a second round trip.
- `get_observations` cost scales linearly with IDs. Always pre-filter with `search` first (the tool's own "3-LAYER WORKFLOW" guidance). Fetching 40 observations without pre-filtering would be ~12,000 tokens.
- Do NOT use `ctx_execute` for file writes (sandbox FS doesn't persist to host). Use Write/Edit for file creation.
- Do NOT use `mcp__desktop-commander__read_file` on large report bodies. Use targeted extraction commands or `ctx_execute_file` instead.

## Forward-looking: Resolution-doc readiness verification gate

**Context.** The Phase 23–24 workflow ends with the Stage-2 consolidation agent delivering the final resolution doc. In the current milestone structure, Phase 25 (first adjudication phase) starts immediately — but nothing verifies that the delivered resolution doc is *fit for adjudication* before five phases of work commit to it. The user plans to insert a lightweight readiness-verification phase between Phase 24 and Phase 25 to close this gap.

### What the phase does

1. **Verify the resolution doc exists and is complete.** Check that every required section (per the consolidation prompt's output-contract specification) is present and non-empty. Check that the header inventory correctly names all inputs received.
2. **Verify cross-reference integrity.** The resolution doc should cite specific sections of the research package and individual reports. Spot-check a sample of citations to confirm they point at real content.
3. **Verify output-contract conformance.** The consolidation prompt specifies a section structure (Executive Summary, per-question resolution, agreement classification, dissenting-opinion register, additional-input-needed register). Confirm every required element is present.
4. **Produce a preview/map for downstream phases.** Document where the resolution doc lives, what each section provides, and how Phases 25–29 should navigate it (e.g., "Q-A1 resolution is in §3.1; Q-B1 is in §3.4; the dissenting-opinion register is in §5").
5. **If the doc fails any check**, return it to the external consolidation agent with a specific fix list. Do not start adjudication until the doc passes.

### Why this matters for Issue-03

Issue-03 will use the same two-stage pipeline. If the resolution doc arrives with a missing section or an internal contradiction, and adjudication (the equivalent of Phases 25–29) starts immediately, the error propagates into spec edits that must later be unwound. A 30-minute readiness check before adjudication is cheaper than a 3-phase remediation after.

### How this fits the milestone structure

This phase is a meta-workflow gate, not a research or adjudication phase. It touches no framework specs, performs no data probes, and makes no semantic decisions. It is purely a verification-and-mapping step that consumes the resolution doc and produces a readiness verdict + a navigation guide for downstream phases.
