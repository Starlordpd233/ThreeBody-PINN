## Summary

Four markdown documentation files converted from LaTeX sources were reviewed at DEPTH level against their original LaTeX sources. The review focused on content accuracy, markdown formatting correctness, pandoc conversion artifacts, cross-file consistency, and issues that would cause verification commands to fail.

**High-level assessment:** The conversions are generally faithful but contain several critical content discrepancies, unresolved conversion artifacts (author comments preserved in body text), formatting regressions in tables and math, and cross-document inconsistencies that could mislead implementers. The most severe issues are in `pinn_architecture.md` where an incorrect SIREN weight initialization formula appears in the summary table (contradicting the body text and the original LaTeX), and in `stage_strat_revision.md` where an editorial author comment was preserved in the converted body.

## Critical Issues

### CR-01: Incorrect Hidden Layer Weight Initialization Formula in Summary Table

**File:** `pinn_instruction/markdown_conversion/pinn_architecture.md:287`
**Issue:** The "Weight Init. (Hidden)" row in the consolidated summary table (Table 2) shows `U[-hidden_omega_0/(6*n_in), hidden_omega_0/(6*n_in)]`, which is NOT equivalent to the correct SIREN formula `U[-sqrt(6/n_in)/hidden_omega_0, sqrt(6/n_in)/hidden_omega_0]` used in the body text (Section 2.2). With `hidden_omega_0 = 1`, the correct formula evaluates to `U[-sqrt(6/n_in), sqrt(6/n_in)]`, while the table formula evaluates to `U[-1/(6*n_in), 1/(6*n_in)]`. These differ by a factor of approximately `6*n_in^(3/2)/sqrt(6)` and would produce completely different initialization scales, potentially breaking trainability of deep SIREN networks.

**Fix:**
```markdown
| Weight Init. (Hidden)   | $U\left[-\frac{\sqrt{6/n_{\text{in}}}}{\text{hidden\_omega\_0}}, \frac{\sqrt{6/n_{\text{in}}}}{\text{hidden\_omega\_0}}\right]$ | The principled initialization for all subsequent SIREN layers... |
```

**Cross-reference:** This is documented as SI-PINN-001 in the file's own Source Issues section, confirming the discrepancy was known but not fixed.

### WR-02: Broken Markdown Table in `review_of_framework.md`

**File:** `pinn_instruction/markdown_conversion/review_of_framework.md:155-163`
**Issue:** The "Comparison of Original vs. Proposed Data-Driven Curriculum Framework" table uses a malformed pipe-table format. The header separator line uses `-------------------------` without leading/trailing pipes, and the table caption `: Comparison of Original vs. Proposed Data-Driven Curriculum Framework` is placed after the table body. Many markdown renderers (including GitHub Flavored Markdown) will fail to render this as a proper table.

**Fix:** Reformat as a standard GFM pipe table with proper header separators:
```markdown
| Aspect | Original Fixed-Threshold Framework | Proposed Data-Driven Framework |
|--------|-----------------------------------|--------------------------------|
| Thresholds | Static, hard-coded values... | Adaptive, derived from data... |
```

### WR-03: Inconsistent Softening Parameter Between Documents

**File:** `pinn_instruction/markdown_conversion/review_of_framework.md:185` vs `pinn_instruction/markdown_conversion/pinn_architecture.md:438`
**Issue:** The `review_of_framework.md` resolves the softening discrepancy by standardizing on `epsilon_soft = 1e-5`. However, the `pinn_architecture.md` (the original architecture plan) still uses `epsilon_soft = 1e-5` in its physics residual and energy calculations. While these now agree, the `review_of_framework.md` claims the `CTL-instruction-final.tex` document specified `epsilon = 1e-10`. Cross-checking the original `ctl-instruction/sections/04_phase1_data_prep.tex` confirms it uses `varepsilon = 10^{-10}` only in potential energy calculations. The resolution in `review_of_framework.md` is correct, but the `pinn_architecture.md` should ideally reference this resolution.

**Fix:** Add a note in `pinn_architecture.md` referencing the unified softening parameter resolution from the review document.

### WR-04: Input Vector Dimension Inconsistency (12D vs 14D)

**File:** `pinn_instruction/markdown_conversion/pinn_architecture.md:821` vs `pinn_instruction/markdown_conversion/review_of_framework.md:199`
**Issue:** The `pinn_architecture.md` summary table states the input vector is "A 14-dimensional vector [t, IC]" and the `review_of_framework.md` (Section 3.3, Issue 19) also describes a "14-dimensional input vector [t, IC]". However, the `pinn_architecture.md` body text (Section 5.2 / Table 2) and the `ctl-instruction` LaTeX source describe a 12-component IC vector (3 masses + 5 invariants + 3 shape invariants + 1 inertia = 12, plus time = 13). The `review_of_framework.md` input vector table lists 13 IC components + time = 14 total. The `pinn_architecture.md` Table 2 says "13-component vector of initial conditions" but then lists only 11 bullet points (3 masses + 5 physical invariants + 3 trigonometrically encoded angles). The dimensionality is inconsistent across documents.

**Fix:** Reconcile the input vector dimension. The `review_of_framework.md` table is the most detailed (14 total = time + 13 IC components). Update `pinn_architecture.md` to match, or add a cross-reference note.
