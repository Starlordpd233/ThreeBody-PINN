**Critical hazard — table separator corruption:** A naive sed pattern that treats *any* non-space, non-pipe character as a "word boundary" will inject em-dashes into long hyphen runs inside GFM table separator rows. For example, `data_quality_assessment.md` line 96 contains:

```
|----------------------|----------------------------------|--------------------------|-------------------------------|
```

A pattern like `s/\([^ |]\)---\([^ ]\)/\1—\2/g` matches every `-` triplet inside the run (each `---` is preceded and followed by `-`, which is neither space nor pipe), producing a corrupted separator like `|—————————————————————|...` that breaks GFM rendering.

**Required approach:** Restrict the replacement to em-dashes between *alphanumeric / closing-paren / opening-paren* characters — i.e., real prose word boundaries. This deliberately excludes `-` itself from the surrounding-character class so hyphen runs in separators are untouched. Run per file:

```bash
# Replace --- with — only when both sides are letters/digits or ()/[] punctuation —
# never when either side is another '-', a space, or a pipe.
sed -i '' 's/\([[:alnum:])]\)---\([[:alnum:](]\)/\1—\2/g' <file>
```

This pattern is intentionally narrow. It will miss two latent edge cases that do **not** occur in the current files but are worth knowing about:
- ` --- ` with spaces on both sides (none exist in the four files).
- `word ---word` or `word--- word` with a space on exactly one side (none exist).

If a future audit surfaces such a case, the fix is a hand edit, not a regex broadening.
