### FINDING-1 — Row 39-10-02's status assertion is vacuous (HIGH)

Row 39-10-02's `awk` is missing its closing brace versus the authoritative text at
`39-10-PLAN.md:115` — a **one-character** transcription loss introduced when 39-10-02
wrote its own row:

- plan:   `… if (id != \"39-10-02\" && status != \"✅ green\") print id}" "$v")"`
- ledger: `… if (id != \"39-10-02\" && status != \"✅ green\") print id" "$v")"`

`awk` aborts with `syntax error … missing }`, writes nothing to stdout, and the enclosing
`test -z "$(…)"` therefore **always passes**. The row cannot fail.

Demonstrated on a temporary copy (the real ledger was untouched): with row 39-01-01 forced
to `❌ red`, the ledger's awk reported clean while the plan's awk correctly reported
`39-01-01`. Consequence: row 39-10-02's green status — both before and after this plan —
proves nothing about the other rows. Its *other* assertions (coverage classify, row
uniqueness) do still execute and pass.

**Recommended fix (owner authorization needed):** restore the single `}` to match
`39-10-PLAN.md:115`. This *strengthens* the row and is grounded in that plan, so it is not
the "weakening" the prohibition guards against. All rows are currently green, so the
restored assertion would pass immediately.

### FINDING-2 — The negated-rg hygiene assertion is inert and self-matching (MEDIUM)

Present in row 39-10-02 and, per the plan's mandated text, in the new row 39-13-02:

```
! rg -q "\*\*R[u]n:\*\*|simulation_data/Data>" "$v"
```

Two compounding issues:

1. **Inert under `set -euo pipefail`.** Bash exempts `!`-inverted commands from errexit, so this line can never abort the command. Verified: `bash -c 'set -euo pipefail; ! true; echo reached'` prints `reached`.
2. **Self-matching.** The needle `simulation_data/Data>` appears in the ledger *as its own pattern literal* inside rows 39-10-02/39-13-02. The sibling alternative is deliberately written `R[u]n` to dodge exactly this — evidence the author knew about self-matching but missed the second needle, which went unnoticed precisely because (1) makes the check inert.

The two defects cancel: were (1) fixed alone, rows 39-10-02 and 39-13-02 would immediately
fail on their own pattern text. **The underlying criterion is independently confirmed
satisfied** — zero `**Run:**` prefixes and zero real angle-bracket placeholders in any row.

## Deviations from Plan

### 1. [Rule 3 — Blocking] `dataset-free.log` capture-time N12 redaction

- **Found during:** Task 39-13-01, step 1.
- **Issue:** Raw stdout of the repository suite contains 4 `/Users/` paths (torch deprecation + two UserWarning tracebacks + a PyTorch CI build path). Row 39-10-01's pre-existing, unmodifiable command asserts `! rg -q "/Users/" "$e"` over the **whole evidence directory**, so a raw capture would fail it.
- **Resolution:** Reused 39-10-01's established substitution verbatim (`$HOME` → literal `$HOME`; `/Users/runner` → `/<ci-runner>`), confirmed by inspecting its retained artifact. Applied **at capture time** in the harness pipeline, so the produced bytes were never personal-path-bearing — this is the producer writing its own bytes, not a post-hoc edit of a written artifact. Added a fail-closed guard that aborts (rather than scrubbing further) if any `/Users/` survives.
- **Why this does not contradict the integrity directive:** the directive scopes byte-for-byte purity to `scan.log`, a single CLI artifact whose redaction is the adapter's production-time invariant. `dataset-free.log` is a harness-assembled capture of 18 commands and has no other producer.

### 2. [Rule 1 — Bug] Audit used the wrong StageQuery source

- **Found during:** Task 39-13-01, step 3 (first audit run, `AttributeError: 'int' object has no attribute 'value'`).
- **Issue:** My audit passed the adapter to `select_stage_records`. The adapter is deliberately **not** a StageQuery — `has_stage(key)` means "is this record staged" and `records_at_or_below(stage)` expects a `StageLabel` enum. `StageIndex` is the canonical seam.
- **Fix:** Built a full-admitted-set `StageIndex` carrying the adapter's blacklist, so the selector's blacklist/non-Set-1a guards are genuinely exercised rather than silently defanged. Not a production defect — no production path passes the adapter directly.

### 3. [Rule 1 — Bug] `independent_sample_parse` false "mismatch"

- **Found during:** Task 39-13-01, step 3.
- **Issue:** My check compared `dt_out` (a float64 `median(diff(times))`) against a **first** diff of the resident **fp32** tensor with a `1e-9` tolerance. Probed: discrepancy `1.79e-09`, below fp32's ~1e-7 representable precision at t≈10. My check was wrong; the data was correct.
- **Fix:** Replaced with a genuine independent parse — re-read `brutus_hierarchical_0000.txt` from disk, re-derive times in float64, and assert `n_snapshots` (126) and exact `measure_dt_out` equality against residency, plus an fp32-appropriate carry check. Result: `match`, `dt_out_measured=0.08000000000000007`, `dt_out_reference=0.08`, `provenance=direct`.

### 4. [Process] Commit-message command substitution

- **Found during:** Task 39-13-02 commit (3-min timeout, no commit created).
- **Issue:** Backticks inside a double-quoted `-m` string are shell command substitution. Verified afterwards that **nothing was damaged**: corpus still 38,017 files, `simulation_data` clean, no stray files, `scan.log` sha unchanged, ledger still staged, HEAD unmoved, and `agent-commit`'s EXIT trap had released the shared lock.
- **Fix:** Re-committed with a backtick-free single-quoted message.

### 5. [Coverage] `dataset-free.log` includes the per-row validation slices
