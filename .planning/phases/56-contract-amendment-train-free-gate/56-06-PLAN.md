Section two — the structural findings that must survive into whatever the owner decides.
Record both, with their provenance in the research document and in the code that now
carries them. First: all six audited cases produce a front index of 0 at initialization
under the healthy amended recipe, because each case's second weight already falls below
the half threshold — so a condition-(iii) test written as a fixed positive-front check
would reject every healthy case, and the healthy-initialization expectation is a graded
weight vector rather than an advanced front. Second: a residual reduction confined to the
late bins cannot move the front index at any magnitude, because a weight depends only on
the exclusive prefix over the bins before it — so any controlled-reduction test that
happens to perturb only late bins will report no sensitivity regardless of design, and
that non-response would say nothing about whether the recipe is healthy. State plainly
that these are mechanistic facts about the ratified formula, verified by direct
computation, and that they are recorded as inputs the owner's ruling will need — not as a
recommendation about what the ruling should be.

its column heading and its row for the SIREN initial-frequency parameter were
deliberately not touched by any task in this phase, that the three candidate mechanisms

row, so any future edit there requires those entries to be re-verified.

its reasoning. State the facts: the Phase 38 test package carries a mechanical

SPEC-06.

Then record this phase's decision and the four reasons behind it. The decision: the guard
is NOT edited by Phase 56, and its two failures are accepted and recorded as
pre-existing. The reasons. First, SCOPE-33 grants framework-specification edits, narrowly
enumerated; a file in the Phase 38 test package is neither a framework specification nor
one of the enumerated items, so editing it is outside the grant on a plain reading.
Second, re-baselining the guard inside the very phase that changes the file it watches
would be self-certification — the same anti-pattern this repository's committed-fixture
integrity guards exist to prevent, and which this phase itself applies to its own
demonstration fixture. Third, Phase 55 set the precedent one week earlier and this phase
follows it rather than diverging without cause. Fourth, choosing a new base reference is
a governance decision about which tree state is the milestone's baseline, which belongs
to a milestone-close or documentation-convention pass rather than to a phase whose grant
is narrow by design.

Close section four by naming the follow-up: the guard should be re-baselined or retired
by whichever later pass carries the authority, and until then any full-suite run of this
repository will show exactly two failures in that file whose messages name the superseded
Phase 38 prohibition. Record the expected failure count and the distinguishing message
text so a future reader can confirm at a glance that a red suite is this known condition
rather than a new regression.
