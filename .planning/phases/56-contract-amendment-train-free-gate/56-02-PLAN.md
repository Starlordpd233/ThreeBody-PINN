Condition (ii) — the deliberately unratified slot. `54-RULING.md`'s re-issued
AC-LOSS-04 requires GATE-04 to fail closed on a degenerate weight vector, but neither
that ruling nor any other source in this repository defines what "degenerate" or
"carrying differential information" means numerically. That decision is GAP-56-01,
status OPEN, awaiting the owner. Build the slot so it cannot be filled by accident in
either direction. `condition_ii_verdict(weights)` raises `NotImplementedError` whose
message names GAP-56-01, states that the pass criterion for condition (ii) is
unratified, and points at
`.planning/phases/56-contract-amendment-train-free-gate/56-GAPS.md` and the four
candidate options recorded there. Nothing else in the module calls it.
`condition_ii_diagnostics(weights, causal_clip_min_weight)` returns a plain mapping of
descriptive statistics over the weight vector — the coefficient of variation of the
tail entries from index 1 onward (index 0 is fixed at 1.0 by construction), whether the
vector is monotone non-increasing, the base-10 span between the largest and smallest
entry, the count of entries strictly above the clamp floor, and a `status` key whose
value is the string `UNRATIFIED`. It performs no comparison against any constant and
returns no verdict-shaped field. Its docstring states in full that these are the
statistics 56-RESEARCH.md Part (b) computed for the six audited cases, that they are
recorded so the owner's eventual ruling has real post-amendment data to rule against,
and that GATE-04 currently treats condition (ii) as measured-but-not-adjudicated rather
than as satisfied.

Condition (iii) — front capability, not a fixed front value. Implement
`condition_iii_diagnostics` taking the raw bin means, the frozen reference value, the
usual eta / dtype / device / t_max arguments, a `factors` argument defaulting to
`CONDITION_III_DIAGNOSTIC_FACTORS`, and a `late_bin_start` argument defaulting to 8.
For each factor it scales the normalized bin residuals uniformly, recomputes the
weights through `ratified_causal_weights`, and records the resulting front index using
the probe module's existing front-index helper — the trainer formula, the largest
0-indexed entry whose weight exceeds 0.5 strictly. It separately records the front index
under a reduction applied only to the bins from `late_bin_start` onward. It returns a
mapping with the uniform-response series, the late-bin-only response series, the
unperturbed front index, and a `status` of `UNRATIFIED`. It applies no pass threshold.
Define `CONDITION_III_DIAGNOSTIC_FACTORS` as the reduction ladder 1.0, 0.9, 0.75, 0.5,
0.25, 0.1, 0.05, 0.01, 0.001, and document in the constant's own comment that this
ladder reproduces the sensitivity sweep already published in 56-RESEARCH.md section
b.4, that it is a diagnostic instrument only, and that the reduction magnitude and
response margin a healthy recipe must meet are part of the same open gap.

Write the two structural findings from 56-RESEARCH.md into the function docstring so
they travel with the code rather than only with the planning artifacts. First: all six
audited cases produce an unperturbed front index of 0 under the healthy amended recipe,
because every case's second weight already falls below 0.5, so a fixed positive check
would reject every healthy case. Second: a reduction confined to the late bins cannot
move the front index at any magnitude, because a weight depends only on the exclusive
prefix over the indices before it — so a no-response result from a late-bin-only
perturbation is an artifact of the formula's structure and carries no information about
recipe health.

Extend `gate04_verdict` only where it is grounded: a weight vector so degenerate that
the front index cannot be computed — a non-finite entry — is already a BLOCK from
56-01's finiteness rule; assert that path explicitly in the docstring under condition
(iii). Add no other condition-(iii) rule. Reduce `unratified_conditions` from the
two-element tuple 56-01 emitted to a one-element tuple naming condition (ii) only:
condition (iii)'s structure is now present and its grounded fail-closed rule is wired,
while condition (ii) remains unadjudicated. Update the `gate04_verdict` docstring's
rule-ordered list accordingly, keeping the statement that a PASS carrying a non-empty
`unratified_conditions` is an INCOMPLETE result.

Populate the two condition-diagnostic fields on each case result inside `evaluate_case`
from the two new functions.
