## How every run in this plan is launched

Each task uses the same steps, in this order.

1. **Check the precondition.** The task's precondition is checked read-only. If it is unmet, halt with a blocking-human checkpoint: the run waits for the owner's next weekend AC window. A battery or window refusal is a deferral, never a failure to work around.
2. **Inspect the output directory first,** and take the next action that "Run states and next actions" in 66-03-PLAN.md gives for its state. This makes the plan safe to resume. That table covers every state a launch can reach:
   - no directory: launch;
   - a receipt and no attempt: wait while the launch is live; otherwise it counts as incomplete;
   - a running attempt: wait while the launch is live; otherwise it counts as incomplete;
   - a launch still live 15 minutes after its cap ran out: stop and report for the owner;
   - an incomplete attempt: the retry rule below, except that a cap expiry stops and goes to the owner;
   - a published attempt: verify it (step 5). A clean run is committed, a mechanical failure uses the retry rule, and a setting problem halts for the owner without using it;
   - a failing retry: stop and report for the owner.
   A published attempt is never relaunched, and a used directory is never edited or launched into again.
3. **Launch exactly once, detached:** run the launch command `<home>/miniforge3/envs/pinn-train/bin/python -B -m pinn.verification.diagnostic_power launch --registration <registration> --output <dir>/record.json`, from <home>/Desktop/3_body_problem/.worktrees/trainex, through the detached launch wrapper of 66-03-PLAN.md ("The detached launch wrapper"). Its survival test passed in task 66-03-02, so it need not be repeated.
   - The wrapper puts the run in its own session and process group, so an idle or ended agent session cannot terminate it.
   - The session scratch log, outside the repository, keeps the complete output and the LAUNCH-EXIT line. Record the start and end times and the working directory beside it (global CLAUDE.md, expensive-validation evidence rule).
4. **Wait for completion** by inspecting `<dir>` at a modest interval until the run-state table gives an action other than wait. The harness's supervised cap ends the run within whole_run_cap_seconds plus its termination grace, and the table ends any wait 15 minutes after the cap ran out. Run no test suite, no second run and no other heavy job meanwhile (66-RESEARCH.md Pitfall 8).
5. **Verify read-only:** verify-result against the run's registration, then check-run on the directory, then `stat` of record.json, which must be below 10,485,760 bytes before anything is staged. Use check-run, never read-run, in this plan. It runs the same record and directory checks but prints no E, tier, branch or similarity value, so no score is seen before all three runs exist (D-07). Reading the results is plan 66-05's.
6. **Commit the four files** per the commit protocol:
   - GIT_AGENT_OWNED_PATHS set to that one output directory, as the task names it;
   - the subject the task names;
   - a body with the four SHA-256 values, the completed steps, seconds_per_step, the wall time from the attempt timestamps and the record bytes.
7. **Record only mechanical facts** in the SUMMARY: steps, cadence entries, access counts, timing, receipt and attempt timestamps, record bytes. Branch reading belongs to plan 66-05.

The retry rule, from 66-PREDICTION.md "Mechanical failure and retry":
- One retry per role, with identical settings and the same page.
- First write evidence/exp01/<role>-retry1-registration.json with a fresh scratch build. Commit it per the commit protocol, with GIT_AGENT_OWNED_PATHS=.planning/phases/66-small-network-control/evidence/exp01/<role>-retry1-registration.json and subject evidence(66-04): register the single retry for the <role> run, and with a body giving the failed attempt's reason and the retry registration's SHA-256. Then run check-registration, then run once, through the wrapper, into evidence/exp01/<role>-retry1/record.json.
- A second failure, or any cap expiry, stops this plan and is reported to the orchestrator for the owner. The steps, cap, orbit and seed are never changed.
- Once a role has used its retry, the task's verify commands, its acceptance checks and task 66-04-03's all-three checks use <role>-retry1-registration.json and <role>-retry1 in place of the role's first registration and directory. Plan 66-05 passes the retry directory the same way.
- A setting problem does not use the retry. Commit the run's four files, then halt this plan for the owner as the run-state table says. The remaining runs wait for the owner's answer (page section 7; D-07).
