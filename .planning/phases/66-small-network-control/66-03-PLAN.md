## The detached launch wrapper (every launch in Phase 66)

Every Phase 66 launch runs detached, so that an idle or ended agent session cannot terminate it. This host has SIGTERM'd an agent's background processes when its session went idle. A foreground launch can also outlive the shell tool's own time limit.
- The wrapper: from the trainex root, run the pinned interpreter with an inline -c program. It opens the session scratch log for append and calls subprocess.Popen on ["/bin/sh", "-c", "<the launch command>; echo LAUNCH-EXIT=$?"], with start_new_session=True, stdin=subprocess.DEVNULL, and stdout and stderr both going to the log. It then prints the child PID and exits without waiting. start_new_session gives the run its own session and process group, so a SIGTERM or SIGHUP sent to the agent's process group never reaches it. The log keeps the launcher's complete output and ends with the LAUNCH-EXIT line.
- The survival test, run once before the first launch (task 66-03-02):
  1. Start /bin/sleep 120 through the same wrapper, from inside a subshell started with job control (set -m), so that the subshell has its own process group.
  2. Send SIGTERM to that subshell's process group.
  3. Confirm with kill -0 that the sleep still runs, and with ps -o pid=,pgid= that its process-group ID equals its own PID and differs from the subshell's.
  4. Stop the sleep with kill.
  Keep the output in the scratch log, and record the PIDs and PGIDs in the SUMMARY. If the sleep died, stop and report to the orchestrator: launches are not detached, and no run may start.
- Waiting: poll the output directory at a modest interval until "Run states and next actions" below gives an action other than wait. Then read the log for POWER-OK or POWER-REFUSED, FIT-RUN-COMPLETE, FIT-RUN-INCOMPLETE or FIT-REFUSED, and LAUNCH-EXIT.

### Run states and next actions

Inspect the output directory before every launch and whenever a wait ends, and take the action this table gives for its state. The table covers every state a launch can reach, for the timing run and for each experiment run alike. Never edit, delete or launch into a directory that a launch has created: a used directory refuses a second launch at its exclusive receipt.

A launch is live while `ps` shows a process carrying pinn.verification.diagnostic_power or pinn.verification.diagnostic_fit (the wrapper's shell, the launcher, caffeinate and the fit command each carry one), or while the pid that attempt.json records is alive and `ps -o command= -p <pid>` shows the pinned interpreter. That pid is the fit worker, a spawned child whose command line carries neither name. Only the worker and the fit command ever mark an attempt, so once a launch is not live, nothing will mark it. The supervisor ends a worker within 15 seconds of the cap (diagnostic_fit.py _run_supervised: a 10-second terminate grace, then a 5-second kill grace).

"The single retry" is page section 7: one fresh committed registration per role, with identical settings and the same page, run once into a new directory. Its steps are in task 66-03-02 for the timing run and in 66-04-PLAN.md for the experiment runs. Why a setting problem halts without the retry: the step-0 bandwidth check failed, so the run did not test the network the page registered (timing page section 4). A retry with identical settings rebuilds the same initial network from the same seed, so it cannot clear the failure. The halt is registered on the timing page (section 7) before any run. check-run reports the problem without showing any score, and the problem is fixed at step 0, before training. Output movement is how much the network's output moves over time, as a fraction of how much the real orbit moves (the DIAG-09 logger records it at every cadence step). A false "settled" would wrongly send a run to the 66.1 proposal.
