## Decisions this plan carries

1. **The digest-pinned `diagnostic_fit.py` is edited, and the Phase 65 smoke registration becomes historical (orchestrator note 5, decided here).** The registry lookup lives in `validate_smoke_settings`, which every admission path reaches (`_cmd_run`, `run_registered_smoke`, `verify_fit_result`, `check_fit_registration`). It resolves a name only against the sealed catalog in `diagnostic_variants.py`. Both files are pinned by the smoke registration, so any design that admits a second variant through the existing door changes a pinned byte. The non-editing alternatives are not equally small. One is a roughly 300-line clone of the admission, supervision and verification code, which duplicates exactly the safety logic Phase 65 tested and invites drift. The other rebinds module globals across the spawn boundary of the supervised worker, which is opaque and fragile. So the edit is accepted, confined to about 45 lines: the five sites of 66-PATTERNS.md section 4 plus Site F, the loss-trace stride (decision 4). The safeguards are these: the other four smoke-pinned modules stay byte-identical; the 11 Phase 65 evidence files stay unchanged; and `test_historical.py` checks the historical identity at the commit that added the smoke record, `84128fe2`. That commit, not the registration's introducing commit `ac4358cb`, is the right anchor (PATTERNS flag 11). This matches the letter of D-11 ("The Phase 65 evidence, hashes and registrations stay unchanged"): no Phase 65 file changes. It also matches `65-CLOSEOUT.md:86-89` ("If their implementation touches a pinned dependency, it must use a fresh registration; historical smoke evidence stays unchanged"), and the closeout's precedent for the probe registration (decision 3). Every Phase 65 refusal still holds. The smoke's live refusal is the guard working as designed. The last live pass and the first live refusal are captured in this plan's SUMMARY. That historical-status record also names the probe registration, `evidence/probe/expectations.json`, the only other Phase 65 registration that pins `diagnostic_fit.py` (its code_dependencies entry 3). Its pin already differed from the live file before Phase 66, and `65-CLOSEOUT.md` line 109 records its live check-registration as PROBE-REFUSED, so it was already historical (closeout decision 3). This plan neither runs nor changes that check. Plan 66-03 restates them on the committed timing page, because `65-CLOSEOUT.md` must stay byte-identical.
2. **Reuse-condition stance (65-CLOSEOUT.md defect table).** WR-01 is a precondition for graded use only (D-11). WR-02 and WR-05 govern new probe registrations; Phase 66 registers fits. WR-03 and WR-04 stay deferred, because Phase 66 runs `verify-result` only on records its own harness wrote at its own registered paths, and a traceback there is a failure, never a success. WR-06 is not triggered: the same loader and time transform are used. IN-01 is not triggered: the schema literal stays `phase65-fit-registration/v1`, the window endpoints stay numeric, and the two new keys (`variant_registry` and `loss_trace_stride`) are validated strictly.
3. **The launcher runs the fit CLI as a child (`subprocess.run` with a fixed argv list), not by replacing its own process.** This is the tracked Phase 60 launcher precedent. It keeps the receipt write strictly before the child starts, and tests can inject it. The interpreter path is never written to a receipt, because the redaction guard refuses home-directory text.
4. **Record size is bounded at its source, so run length follows D-08 alone (checker blocker 2; orchestrator ruling).** The harness records the loss after every step, and that trace is the only part of a record that grows with the step count. At the step counts the one-hour cap allows, an every-step trace would push a record toward the repository's 10 MiB staged-blob limit (`MAX_BLOB_BYTES` in scripts/git_policy/validate_staged_paths.py), which would have made file size, not need, set the run length. Raising or bypassing that limit is a governance change and is out of bounds. So Site F lets a registration declare `settings.loss_trace_stride`: the record then keeps the loss after every stride-th step plus the final step. Plan 66-02 sets the stride to ceil(N / 10,000), so a record holds at most 10,001 loss entries whatever N is. The loss is context only (D-10), so thinning it changes no score and no reading. The in-memory loss list, and every count derived from it, are unchanged. A registration without the key keeps the Phase 65 every-step trace, so the Phase 65 suite and records are unaffected.
