## Part 3 — Proven problems, in full

Worst first. Each entry is `derived-math` or `literature-cited`, with the offending text quoted.

### IR2-001 — Build plan Phase 38 NET-04 specifies a wrong loss function
- **What's wrong:** The build plan's Phase 38 NET-04 success criterion describes the loss as "three-term loss (data L1/MAE + physics + IC)", which contradicts the locked spec's five-term Huber-based loss.
- **Where:** `v2.0-build-plan.md` Phase 38 NET-04 (success criterion 4).
- **The proof (quoted text + spec citation):**
  - Build plan text (verbatim): "The three-term loss (data L1/MAE + physics + IC) evaluates in the shared dimensionless system (`t_τ ∈ [-1,1]`, `r' = r/D`, raw-mass `D ≈ 4.6416`) matching the locked spec loss contracts (NET-04)."
  - `pinn_architecture.md` §3 (just below "The default Phase 19 training objective is"): "$L_{total} = L_{data} + \lambda_{IC} \cdot L_{IC} + \lambda_{phys} \cdot L_{phys}^{causal} + \lambda_E \cdot L_E + \lambda_L \cdot L_L$" — five terms, not three.
  - `pinn_architecture.md` §3.1: "The data fidelity loss uses a Huber contract on scaled projected positions: $L_{data} = \frac{1}{N_t} \sum_n \sum_i \operatorname{Huber}_{\delta_r}(r_{\theta,i}'(u_n) - r_i'(u_n))$ ... where $\delta_r = 1$ is the default Huber transition. The previous MAE/L1 data-loss prose is replaced by this Huber contract." — Huber, not L1/MAE; the spec *explicitly replaces* the L1/MAE formulation.
  - `ctl_instruction.md` Phase 2 "Loss Function Formulation" (line ~1722): "$\mathcal{L}_{\mathrm{total}} = \mathcal{L}_{\mathrm{data}} + \lambda_{\mathrm{IC}} \, \mathcal{L}_{\mathrm{IC}} + \lambda_{\mathrm{phys}} \, \mathcal{L}_{\mathrm{phys}}^{\mathrm{causal}} + \lambda_E \, \mathcal{L}_E + \lambda_L \, \mathcal{L}_L$" — same five terms.
- **How serious:** Serious. A builder reading NET-04 literally would (i) omit the energy regularizer `L_E` and the angular-momentum regularizer `L_L` (the two terms that enforce the spec's "soft conservation" design objective), and (ii) use L1/MAE for `L_data` instead of the Huber contract the spec explicitly locked. Both deviations invalidate results: the Phase 43 ACC-03 acceptance gate (`ε_H > 1e-5` reject) would almost certainly fail because nothing in the three-term L1/MAE loss penalizes energy drift.
- **Which file it points at:** The build plan (`v2.0-build-plan.md`).
- **Stops the build?** must-fix-first. A wrong loss function in Phase 38 propagates to every later phase that trains or evaluates the model; there is no point running Phase 40–43 against a wrong loss.
- **Suggested fix (suggestion, not a decision):** Rewrite NET-04 success criterion 4 to read: "The five-term loss ($L_{data}$ Huber $\delta_r=1$ + $\lambda_{IC} L_{IC}$ squared-error + $\lambda_{phys} L_{phys}^{causal}$ + $\lambda_E L_E$ Huber $\delta=1.0$ + $\lambda_L L_L$ componentwise Huber $\delta=1.0$) evaluates in the shared dimensionless system ($u \in [0,1]$, $\tau = 2u-1 \in [-1,1]$, $r' = r/D$, raw-mass $D \approx 4.6416$) per `pinn_architecture.md` §3 and `ctl_instruction.md` Phase 2 'Loss Function Formulation'." (PB-1 Option A.)

### IR2-002 — Stage 0 `s_min > 2` criterion is geometrically incompatible with the hierarchical IC sampling (`locked-decision challenge`)
- **What's wrong:** Stage 0's admission criterion `s_min > 2` (in code units) cannot be satisfied by any hierarchical-trajectory IC produced by the locked `sampling_method.md` pipeline. Under the literal criterion, Stage 0 is empty.
- **Where:** `ctl_instruction.md` §"Multi-Stage Data Stratification by Difficulty", Stage 0 criteria bullet: "Minimum Initial Separation: $s_{\min}>2$ (in code units) to avoid any incipient close approaches."
- **Steelman first (the strongest case FOR the locked choice):** The criterion is well-intentioned. The intent — stated in the spec's own prose — is to "avoid any incipient close approaches" at $t = 0$, which is a legitimate filter for the easiest stage. For a hierarchical triple the genuine close-approach risk is between the inner-binary COM and the tertiary, not within the inner binary itself; the inner binary is *bound* and orbits stably at small separation by design. So the *intent* of the gate is sound: exclude systems that will experience a close encounter in the near term. The locked choice was made deliberately by the v1.x milestones and the spec author explicitly defines `s_min` as a "minimum initial separation" diagnostic. The design is not arbitrary.
- **The proof (derived-math, quoted text + worked derivation):**
  - `sampling_method.md` Stage 1 "Hierarchical Initial Conditions Generation" step 3 (quoted): "Sample inner semi-major axis $a_{\rm inner}\sim U(0.1,0.3)$, set $a_{\rm outer}=\mathcal{R}\,a_{\rm inner}$." Step 4 (quoted): "$r_{\rm inner}=a_{\rm inner}\bigl(1-e_{\rm inner}\cos M_{\rm inner}\bigr)$" with "$e_{\rm inner},e_{\rm outer}\sim U(0,0.3)$". So $r_{\rm inner} \in [a_{\rm inner}(1-0.3),\, a_{\rm inner}(1+0.3)] = [0.7\,a_{\rm inner},\, 1.3\,a_{\rm inner}] = [0.07,\, 0.39]$ in raw $G=1$ units.
  - `ctl_instruction.md` Step 3 item 1 (quoted): "$s_{\min} \;=\; \min_{1\le i<j\le 3} \lVert \mathbf r'_i - \mathbf r'_j \rVert$" computed from "*scaled* initial conditions $\{(\mathbf r'_i,\mathbf v'_i)\}$". For a hierarchical triple, $r_{\rm outer} = \mathcal{R}\, r_{\rm inner}$ with $\mathcal{R} \in U(\max(3, \cdot), 10) \geq 3 \gg 1$, so the minimum pairwise separation is the inner-binary separation: $s_{\min} \approx r_{\rm inner}$.
  - `ctl_instruction.md` Step 2.5 (quoted): "$D = (G T^2)^{1/3}$ ... With $G = 1$, $D \sim 4.6416$." And "$r_i' = r_i^g / D$". So $s_{\min}$ (scaled) $= r_{\rm inner}/D \in [0.07/4.6416,\, 0.39/4.6416] = [0.0151,\, 0.0840]$.
  - `ctl_instruction.md` §"Multi-Stage Data Stratification" Stage 0 (quoted): "Minimum Initial Separation: $s_{\min}>2$ (in code units)"; "code units" = "dimensionless" per the same section's note ("All data is normalized to dimensionless code units for training ... positions and distances scaled by a characteristic length").
  - $0.0840 < 2$, so no hierarchical trajectory in the spec's sampling envelope satisfies $s_{\min} > 2$ in scaled code units.
  - Empirical confirmation in the spec itself: `ctl_instruction.md` §"A Glimpse at the Data" gives a sample hierarchical IC. Computing its pairwise distances from the listed 21 numbers (masses $m_1{=}1.349, m_2{=}0.307, m_3{=}1.344$; positions $\mathbf r_1{=}(-0.969, 0.008, -0.015)$, $\mathbf r_2{=}(-0.662, -0.005, 0.007)$, $\mathbf r_3{=}(1.135, -0.002, 0.003)$ in raw units): $|r_1{-}r_2| \approx 0.308$, $|r_1{-}r_3| \approx 2.105$, $|r_2{-}r_3| \approx 1.797$. So $s_{\min}$(raw) $= 0.308$, $s_{\min}$(scaled) $= 0.308/4.6416 \approx 0.066$. Even in *raw* units, $s_{\min} = 0.308 < 2$. The spec's own sample trajectory fails its own Stage 0 gate.
- **How serious:** Serious. Stage 0 is the build's only training population (the viability slice is Stage-0-first per `v2.0-build-plan.md` "Build discipline & grounding"). An empty Stage 0 halts the build at Phase 39 (DATA-06: "flags an under-populated Stage 0 as a fatal-class risk").
- **Which file it points at:** The spec (`ctl_instruction.md`).
- **Stops the build?** must-fix-first. The build can start (Phase 37–38 do not need Stage 0 data) but cannot complete Phase 39 without resolving this. Phase 39 is on the critical path to every later phase.
- **Suggested fix (suggestion, not a decision):** Lower the Stage 0 threshold to `s_min > 0.01` (scaled code units), matching `sampling_method.md` §4's `MIN_DISTANCE_THRESHOLD = 0.01` pre-screening floor — this preserves the "exclude near-collisions" intent and aligns Stage 0's geometric gate with the data-generation gate that already exists. (PB-2 Option A.) The other Stage 0 criteria ($E < -0.5$, $L/L_{\max} > 0.5$, $0.7 \leq Q \leq 1.3$) are well-posed and need no change.
- **Flag:** `locked-decision challenge` (Tier 2; steelman + proof + flag all present).

### IR2-004 — Build plan Phase 39 DATA-02 summarizes the Step-1A admission gate incompletely
- **What's wrong:** The build plan's Phase 39 DATA-02 describes the Step-1A admission gate as "`final_timestep ≥ 9.5` and NaN/Inf filter", omitting the spec's clauses for blacklist exclusion (clause 1), DATA-05 quarantine (clause 2), the conservation gate (clause 5, the family's *only* reject gate), physical-invariant gates (clause 6), and grid-consistency warnings (clause 7).
- **Where:** `v2.0-build-plan.md` Phase 39 DATA-02 (success criterion 2).
- **The proof (quoted text + spec citation):**
  - Build plan text (verbatim): "the Step-1A admission gate (`final_timestep ≥ 9.5`) and NaN/Inf filter run at load with logged admitted/rejected/quarantined/dropped counts, and a `data_version_hash` mismatch is a hard refusal, never a silent proceed (DATA-02, DATA-03)."
  - `ctl_instruction.md` §"Step 1A — Trajectory Admission Gate" lists seven clauses: (1) Identity & blacklist; (2) Data-remediation quarantine; (3) Structural integrity (`≥ 2` snapshots, `3` body rows, finite values, monotone timestamps); (4) Completeness (`final_timestep ≥ 9.5`); (5) **Conservation gate** — "REJECT if `SCS > -5` (equivalently `eps_H > 1e-5`)"; (6) Physical invariant gates (mass invariance, IC↔Brutus `t=0` mass gate); (7) Grid-consistency (WARN level). Clause 5 is described as "the family's only reject gate" — i.e., the gate that actually excludes bad trajectories on physics grounds.
  - The build plan's summary mentions only clause 4 (completeness) and a paraphrase of clause 3's finite-values check ("NaN/Inf filter"). It omits clause 5 (the conservation reject gate), clause 1 (blacklist — 65 IDs), clause 6 (mass-invariance, IC↔Brutus), and clauses 2/7.
- **How serious:** Minor. The spec is authoritative, and a builder reading `ctl_instruction.md` Step 1A would implement all seven clauses. The risk is a non-expert builder reading only the build plan and implementing the gate as a completeness+finite check, which would admit trajectories that fail the conservation gate (and thus contaminate training with high-energy-drift trajectories — exactly what the gate is designed to exclude).
- **Which file it points at:** The build plan (`v2.0-build-plan.md`).
- **Stops the build?** n/a (Minor).
- **Suggested fix (suggestion, not a decision):** Reword DATA-02 success criterion 2 to: "The full Step-1A admission gate (clauses 1–7: identity & blacklist, DATA-05 quarantine, structural integrity, completeness `final_timestep ≥ 9.5`, conservation gate `eps_H ≤ 1e-5` reject, physical-invariant gates, grid-consistency WARN) runs at load with logged admitted/rejected/quarantined/dropped counts, and a `data_version_hash` mismatch is a hard refusal."

### IR2-005 — Build plan Phase 39 DATA-05 batch-constructor description is ambiguous about whether collocation is per-trajectory or continuous
- **What's wrong:** The build plan's Phase 39 DATA-05 describes the collocation set as "16 lookahead with the `has_stage(k+1)` guard, 4096 pts", which reads as if collocation points are drawn from the 16 lookahead trajectories' snapshots — contradicting the spec, which defines collocation as continuous samples from $[0, T]$.
- **Where:** `v2.0-build-plan.md` Phase 39 DATA-05 (success criterion 4).
- **The proof (quoted text + spec citation):**
  - Build plan text (verbatim): "The replay/lookahead batch constructor emits the two independent point sets — data-fidelity (240 replay, 8192 pts) vs collocation (16 lookahead with the `has_stage(k+1)` guard, 4096 pts) — with 50/50 uniform + acceleration-weighted time sampling on both, per LOOP-01/02/03 (DATA-05)."
  - `ctl_instruction.md` §"Phase 2a Mini-Batch Construction", "Phase 34 contract: data versus collocation points (LOOP-02)": "1. **Data-fidelity points**: sampled from the discrete BRUTUS trajectory snapshots (the replay/lookahead trajectories above), used for the Huber data loss $\mathcal{L}_{\text{data}}$. 2. **Collocation points**: continuous samples from $[0,T]$ for the physics residual $\mathcal{L}_{\text{phys}}^{\text{causal}}$ and the energy residual $\mathcal{L}_E$ (energy reuses the physics collocation set)."
  - The spec is unambiguous: collocation is continuous from $[0, T]$, independent of which trajectories are in the batch. The build plan's parenthetical ties collocation to "16 lookahead with the `has_stage(k+1)` guard", which (reading literally) would mean collocation is sampled from the 16 lookahead trajectories' snapshot times — defeating the PINN purpose of enforcing physics everywhere, not just at data points.
  - Additional smaller inconsistency in the same sentence: "data-fidelity (240 replay, 8192 pts)" — the data-fidelity set actually draws from 240 replay + 16 lookahead = 256 trajectories (the 16 lookahead set is part of the data-fidelity set per LOOP-01, not separate). $256 \times 32 = 8192$ works arithmetically; $240 \times 32 = 7680$ does not. So the build plan's "240 replay, 8192 pts" omits the 16 lookahead from the data-fidelity count.
- **How serious:** Minor. The spec is authoritative; a builder cross-referencing `ctl_instruction.md` LOOP-02 would implement collocation correctly. But the build plan's phrasing is misleading enough that a non-expert builder reading only DATA-05 could implement collocation as snapshot-time sampling, which would invalidate the physics-residual loss.
- **Which file it points at:** The build plan (`v2.0-build-plan.md`).
- **Stops the build?** n/a (Minor).
- **Suggested fix (suggestion, not a decision):** Reword DATA-05 success criterion 4 to: "The replay/lookahead batch constructor emits two independent point sets — data-fidelity points sampled from the discrete BRUTUS snapshots of the 240 replay + 16 lookahead (= 256) trajectories, $\sim$8192 pts at $n_{\text{pts}} = \min(32, n_{\text{snapshots}})$ per trajectory; and collocation points sampled continuously from $[0,T]$, 4096 pts — with 50/50 uniform + acceleration-weighted sampling retained on the data-fidelity set per LOOP-01/02/03 (the mandatory 50/50 mixed continuous collocation sampler remains deferred per LOOP-03)."

## Part 7 — Side-list (empirical doubts & their tests)

Honest doubts that paper cannot settle, each with a quick empirical test. These feed the build's verify ladder / Stage-0 pilot — extra things to watch in tests the build already runs.

### SL-1. MPS double-backward kernel coverage for the SQR-SkipResNet-SIREN architecture
- **(a) The doubt:** Does PyTorch 2.12's MPS backend support double-backward (second-order AD) for the specific operations in this net — `sin` SIREN activation, `LayerNorm(elementwise_affine=False)`, element-wise square (the `p=2` power term on the skip path), and the second-order residual `d²r'/du²`?
- **(b) Why paper cannot settle it:** MPS operation coverage changes by PyTorch version; the spec targets 2.12 but the exact coverage matrix for *this* operation sequence isn't documented in the official PyTorch MPS feature matrix. The `trainex-r1a-resolution-doc.md` flags this as U-9 ("Open until the §10.3 probe runs on-device with fallback unset").
- **(c) The quick empirical test:** Run the Phase 37 ENV-03 §10.3 componentwise-AD probe on MPS with `PYTORCH_ENABLE_MPS_FALLBACK` **unset**. *Bad result looks like:* the probe crashes with "operation not implemented on MPS" / returns NaN/Inf / produces a `relative_error` larger than the fp64-CPU reference arm by more than ~1e-4 (the R-6 tolerance ruling the owner must ratify as part of D1-p).
- **(d) Confidence note:** Owner-carved (D1-p); the dual-arm probe is the designed resolution mechanism. The fp64-CPU branch is the in-framework escape if MPS double-backward fails.

### SL-2. Actual Stage 0 population after IR2-002 resolution
- **(a) The doubt:** Even after the owner revises the `s_min > 2` criterion (PB-2), how many hierarchical trajectories actually satisfy *all four* Stage 0 criteria ($E < -0.5$, $L/L_{\max} > 0.5$, $0.7 \leq Q \leq 1.3$, revised $s_{\min}$)? Is the population large enough to train (the spec gives no minimum)?
- **(b) Why paper cannot settle it:** Stage 0 population depends on the actual data, which is verified-empirically in `DATASET-CONTEXT.md` for counts but not for invariant distributions. The spec marks stage counts as "claimed" pending the FUT admitted-set EDA.
- **(c) The quick empirical test:** Run the Phase 39 DATA-06 Thrust-A scan with the revised Stage 0 criteria. *Bad result looks like:* Stage 0 has fewer than ~100 trajectories (a rough floor for training a 727K-parameter network on a 9D output space; below this, overfitting risk is high). The build plan already flags "under-populated Stage 0 as a fatal-class risk" — the test is to define what "under-populated" means numerically.
- **(d) Confidence note:** Medium. The hierarchical sampling is designed to produce stable triples, so $E < -0.5$ and $Q \approx 1$ should be common; the $L/L_{\max} > 0.5$ criterion may be the next filter. But the joint distribution is unknown without the scan.

### SL-3. Accumulate-in-closure vs. true full-batch L-BFGS convergence equivalence
- **(a) The doubt:** The spec says stages 0–2 use "standard full-batch L-BFGS" but `trainex-r1a-resolution-doc.md` D5-a interprets this as "accumulate-in-closure" (mini-batch accumulation within the L-BFGS closure, with the line search seeing accumulated gradients). Are these convergence-equivalent for this net + loss?
- **(b) Why paper cannot settle it:** L-BFGS convergence under gradient accumulation is an empirical question; the line-search behavior can differ when gradients are accumulated vs. computed in a single forward pass.
- **(c) The quick empirical test:** On a small Stage-0 sub-batch (e.g., 32 trajectories), run L-BFGS to convergence both ways: (i) single-graph full-batch (if it fits in 24 GB — it should for 32 trajectories) and (ii) accumulate-in-closure over 8 mini-batches of 4 trajectories. Compare the final loss and the trajectory of the line-search step sizes. *Bad result looks like:* accumulate-in-closure converges to a significantly higher loss (e.g., >2× the full-batch loss) or the line search stalls (step size → 0 prematurely).
- **(d) Confidence note:** Low-Medium. The accumulate-in-closure approach is standard practice for L-BFGS on large datasets; the doubt is whether it's equivalent *for this specific net + loss landscape*.

### SL-4. Causal-weight underflow for chaotic stages (4–6)
- **(a) The doubt:** The causal weight `w_n = exp(-η_c · Σ_{m<n} stopgrad(R̄_m))` with `η_c = 1` can underflow to 0 for chaotic stages where residuals are large. If `w_n = 0` for `n > some threshold`, the physics loss is effectively zeroed at late times — the network has no incentive to fit the tail of the trajectory.
- **(b) Why paper cannot settle it:** Depends on the actual residual magnitudes at training time, which depend on the network's initialization and the data.
- **(c) The quick empirical test:** During the Phase 40 Stage-0 training (which has small residuals, so underflow is unlikely) AND during any later chaotic-stage pilot (if attempted), instrument the causal weights `w_n` and log the fraction that underflow to 0. *Bad result looks like:* > 50% of `w_n` are 0 for `n` in the second half of the trajectory, indicating the causal weighting is silently discarding late-time physics.
- **(d) Confidence note:** Medium. The spec explicitly acknowledges this (U-6: "causal-weight underflow clip bound" is owner-pending) and requires "Clip the causal exponent to avoid underflow" — but the clip bound itself is deferred to FUT. The test would also calibrate the clip bound.

### SL-5. Dual-ε (training vs validation) interaction for close-encounter stages
- **(a) The doubt:** The training-time Hamiltonian `H_ε_train` (with `ε_train = 1e-5`) and the validation-time Hamiltonian `H_ε_inv` (with `ε_inv = 1e-10`) differ. The training loss `L_E` minimizes drift in `H_ε_train`; the validation gate `ε_H` measures drift in `H_ε_inv`. For close-encounter trajectories (where pair separations approach `ε_train = 1e-5`), these two quantities diverge — minimizing one may not minimize the other.
- **(b) Why paper cannot settle it:** The interaction depends on the actual close-encounter frequency and severity, which is dataset-dependent.
- **(c) The quick empirical test:** For Stage 0 (no close encounters by design — `s_min > 2` or revised), this is a non-issue. For any later chaotic-stage pilot, after training, compute both `H_ε_train` drift and `H_ε_inv` drift on the held-out test set and compare. *Bad result looks like:* `H_ε_train` drift is below the `ε_H = 1e-4·S_H` loss threshold but `H_ε_inv` drift exceeds the `1e-5` validation gate — the network passes training but fails validation.
- **(d) Confidence note:** Low for Stage 0 (no close encounters); Medium-High for Stages 4–6. This is a deferred concern — the build is Stage-0 only — but it should be on the watchlist for the full platform.

### SL-6. Blacklist training-time consumption
- **(a) The doubt:** `DATASET-CONTEXT.md` flags blacklist training-time consumption as `claimed-unverified`: the dataset's readiness-check tooling loads `problematic_ics_blacklist.json`, but "the current Brutus batch runners do **not** load it." The spec (`ctl_instruction.md` Step 1A clause 1) *requires* the DataLoader to load it at init and exclude 65 IDs (2 hierarchical + 63 standard). Will the v2.0 build's Phase 39 adapter actually load and enforce the blacklist?
- **(b) Why paper cannot settle it:** The build plan's Phase 39 DATA-02 summary omits the blacklist (IR2-004), so it's unclear whether the builder will implement clause 1. The spec is authoritative, but the build plan's silence is a risk signal.
- **(c) The quick empirical test:** Audit the Phase 39 DataLoader code for `problematic_ics_blacklist.json` loading at init, schema validation (exactly keys `hierarchical` and `standard`), and per-`physical_key` exclusion. Then run the loader and verify the 65 IDs (2 hierarchical + 63 standard) are excluded from the admitted set. *Bad result looks like:* blacklist file is not loaded, or loaded but not enforced, or schema validation is missing — any of the 65 blacklisted ICs appears in an emitted training batch.
- **(d) Confidence note:** Medium-High. The spec contract is fail-closed (missing/malformed blacklist = hard init failure), so a correct implementation is unambiguous. The risk is the builder not implementing it at all (because the build plan summary omits it).

### SL-7. `data_version_hash` production mechanism
- **(a) The doubt:** The build plan's Phase 39 DATA-03 requires `data_version_hash` mismatch to be a "hard refusal, never a silent proceed". But `trainex-r1a-resolution-doc.md` U-12 notes the hash *production* mechanism is open (v1.5 PIPE-XX, not attached). If the hash isn't produced and stored in the processed HDF5, the compare-and-refuse check has nothing to compare against.
- **(b) Why paper cannot settle it:** The v1.5 PIPE-XX mechanism is referenced but not attached; whether it's integrated with the v2.0 adapter is a build-time question.
- **(c) The quick empirical test:** Before Phase 39, verify that the processed HDF5 file (or the in-memory adapter's metadata) carries a non-null `data_version_hash` produced by the v1.5 PIPE-XX mechanism. *Bad result looks like:* hash is missing, null, or always the same constant — the compare-and-refuse check is structurally a no-op.
- **(d) Confidence note:** Medium. The build plan's compare-and-refuse contract is correct *given* a produced hash; the doubt is upstream (hash production).

### SL-8. Temporal-sampling Nyquist adequacy for standard-base (Stage 3–4 data)
- **(a) The doubt:** Standard-base trajectories have a median of 61 snapshots over `t ∈ [0, 10.03]`, giving `dt ≈ 0.165` and a Nyquist frequency of ~3 (in units of 1/T = 0.1, so ~30 Hz in code units). For a Keplerian inner binary at separation `r ~ 0.2` (raw) with `m ~ 1`, the orbital period is `P ~ 2π√(r³/(G·M)) ~ 0.4` code-time units, so orbital frequency ~25 Hz — barely below the standard-base Nyquist. The SIREN `first_omega_0 = 30` can represent frequencies up to ~30 Hz, so the network's representable range matches the standard-base Nyquist — but only barely.
- **(b) Why paper cannot settle it:** Depends on the actual orbital frequency distribution of standard-base trajectories, which is dataset-dependent.
- **(c) The quick empirical test:** During any standard-base training run (Stage 3+, out of scope for v2.0 but relevant for the full platform), compute the per-trajectory orbital frequency (from the inner-binary separation and total mass) and compare to the Nyquist frequency `1/(2·dt_out)`. *Bad result looks like:* > 25% of standard-base trajectories have orbital frequency above Nyquist — aliasing would corrupt the training signal for those trajectories.
- **(d) Confidence note:** Low for Stage 0 (hierarchical-base has 127 snapshots, Nyquist ~63 Hz, well above orbital frequency); Medium for Stages 3–4. The spec's SASD metric is designed to flag under-sampled trajectories, but it's provisional (threshold `0.5` pending recalibration).
