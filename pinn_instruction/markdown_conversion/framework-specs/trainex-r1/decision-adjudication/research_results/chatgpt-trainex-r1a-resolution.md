## Executive resolution

The decisive default set I recommend is: **PyTorch as the sole framework spine; TensorBoard only as a secondary view with JSONL as the canonical log; an in-memory Stage-0 data path with `num_workers=0` for the first viability slice; rolling checkpoints with atomic writes, boundary anchors, and always-on failure bundles; a two-phase, closure-shaped optimizer loop that can express the spec’s Adam→L-BFGS regime; accepted-variance reproducibility with a strict CPU debug lane; and explicit curriculum-boundary artifacts and rollback commands.** I endorse most of the prior suggested defaults, but I **override D3**: for the thin first build, the default should be **Option A in-RAM preload**, not the more general auto/streaming path, because the strategy bundle explicitly says the first build should be a minimal Stage-0 viability slice, while the measurements needed to justify streaming are still project-side unknowns. fileciteturn0file0 fileciteturn0file1 fileciteturn0file2 fileciteturn0file3

## STORM multi-perspective scan

The **Apple-Silicon ML practitioner** perspective strongly favors **PyTorch** because the attached research round already records three decisive practical realities: MPS has no fp64 path, PyTorch has the lowest-friction Apple-Silicon training surface plus built-in L-BFGS, and on-device higher-order AD must be verified on the exact MPS graph rather than assumed. The distinctive practitioner warning is that the true first-run risk is not parameter memory but the second-order autodiff graph, so the first build should remove avoidable complexity elsewhere, especially in data loading. fileciteturn0file2 fileciteturn0file3

The **PINN and numerical-methods researcher** perspective is the hardest constraint-setter. From the specs alone, several choices are not genuinely open: the loop must support per-stage **Adam then L-BFGS**, scheduled λ warmups, model-weight carry with **fresh Adam state** at each stage boundary, replay plus lookahead batch structure, componentwise derivatives rather than the forbidden summed-output VJP shortcut, and the §10 acceptance probes. ## Contradictions and robustness map

The biggest conflict sits at **D3**. The practitioner, economist, operations, and operator lenses all prefer the simplest Stage-0 path; the deeper research report argues for a more general streaming design because unified-memory headroom must account for the whole processed dataset and the autodiff graph. The attached materials support both concerns, but they do **not** supply the project-side numbers needed to settle the full-platform memory budget today. The resolving question is therefore empirical: **what are the actual admitted Stage-0 bytes and the measured `M_AD_peak(B,C,dtype)` on the target laptop?** Until that is measured, the strongest grounded recommendation for the thin slice is the simpler in-RAM Stage-0 path, with streaming explicitly deferred rather than prematurely built. fileciteturn0file0 fileciteturn0file2 fileciteturn0file3

A second conflict sits at **D4-c and D7-c**. The operator and operations perspectives want guard-triggered stoppage and, eventually, automated rollback after bad transitions; the adversarial reviewer objects that the thresholds marked as placeholders are not numerically grounded by the attached files. Here the resolving question is also empirical: the r1b findings supply the *need* for guards, but not the numeric values for loss-explosion multiples, consecutive-log windows, disk-floor GB, memory-pressure fractions, or post-promotion divergence windows. The coherent resolution is to build the seams and the typed failure surfaces now, but leave the ⚖ values explicitly blank for later consolidation. fileciteturn0file2 fileciteturn0file3

A third conflict is **determinism versus practical MPS use**. The strict-determinism instinct loses on evidence inside the attached research round: the same round records weaker MPS determinism and performance penalties, while also insisting that the runbook remain usable for a non-expert on a laptop. The resolving question is mostly an owner risk-tolerance question, not a technical mystery: whether the owner wants a slower, CPU-only strict-debug lane available. The robust default is accepted-variance for production runs, plus a strict CPU debug mode as an explicit alternative lane rather than as the main policy. fileciteturn0file2

What all perspectives converge on is more important than where they diverge. They agree that the framework spine should be **PyTorch**, that the build must preserve the spec’s two-phase and boundary-reset contracts, that the smoke test and acceptance probes are essential before long runs, that the run directory must be the main operational artifact, that JSONL should remain the canonical record regardless of dashboard choice, and that the first build should be kept thin rather than prematurely expanded into a full training platform. Those are the highest-confidence recommendations in this report. fileciteturn0file0 fileciteturn0file1 fileciteturn0file2 fileciteturn0file3

## Composed first-run recipe and runbook inheritance

The coherent first run looks like this. Preprocess and admit the data exactly per the locked preprocessing and admission contracts, keeping the offline float64 work on CPU. Run the §10 acceptance probes and the short smoke test first. Then launch a **Stage-0-only** training run from a single keyed YAML using **PyTorch**; use **MPS** if the owner’s separate D1-p channel allows fp32 residuals, otherwise use **CPU float64** under the same framework spine. Preload the Stage-0 tensors in RAM for this first slice, keep `num_workers=0`, run the spec-shaped **Adam phase followed by L-BFGS refinement**, log canonical JSONL plus TensorBoard, checkpoint with rolling files and boundary anchors, keep Tier 1+2 guard seams active with threshold placeholders, and record curriculum transitions in `curriculum.jsonl`. All of that is consistent with the Stage-0 viability-slice strategy and with the locked science contracts. fileciteturn0file0 fileciteturn0file1 fileciteturn0file2 fileciteturn0file3

What the runbook should inherit **now** is concrete and small: use PyTorch; use a single YAML grouped into `stage/opt/loss/run`; launch with `caffeinate -is`; keep the lid open on AC power; run the acceptance ladder and the 5-minute smoke test before any long run; use JSONL as the source of truth and TensorBoard as the dashboard; store checkpoints atomically; treat `stage-k-final` as the rollback anchor; use the documented `--resume ... --hold-stage` style rollback flow; and on any guard stop or uncaught exception, collect the always-on `failure/` bundle rather than improvising. fileciteturn0file1 fileciteturn0file2 fileciteturn0file3
